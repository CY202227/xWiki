# XWiki 技术方案

## 目标与交付

XWiki 为小型知识库提供可追溯、可修订的完整 Wiki 文章。模型负责阅读和提出维护计划，代码负责保存与校验。用户希望使用最多 30B 的模型维护；目前按上下文和操作预算设计，但 API 别名不能证明模型规模，尚无跨模型长期可靠性结论。

交付形态为 Python 服务库和 JSON CLI，宿主可以接入网页、后端和调度器。知识维护是当前重点。RAG、Wiki、PageCard 和页面关系已有基础能力；FAQ、Graph、Tree、PageIndex、MindMap、Timeline、Skills 是后续视图或适配方向，不宣称全部实现。

## 核心数据与职责

SQLite 是权威存储。一份来源有稳定文档 ID、内容哈希、处理版本、状态和原文路径；页/块记录包含正文与可信定位。一篇 Page 保存全文、短摘要、来源、引用、关系和修订。PageCard 是选页摘要，不取代全文。历史实体表用于兼容，公共 API 提供 Page 语义。

来源与文章分开：来源可以更新或失效，但已有文章不会因此自动消失。引用绑定文档 ID、页/块号、内容版本和逐字片段。PDF 使用真实物理页；DOCX 使用正文块号，不能将其称为物理页码。生成的 Markdown 是数据库投影，人工文件改动不会被悄悄覆盖。

## 三条执行路径

摄取路径：收件箱输入 → 本地解析 → 原文归档 → 索引与状态写入 → 成功后消费输入。Markdown/TXT 原生解析，文本 PDF/DOCX 使用可选 MarkItDown。解析失败和不支持的扫描/图片文档保留输入。内容精确去重，同名不意味着替换。

维护路径：扫描任务 → 读取 PageCard → 选择至多 5 篇文章 → 读取全文和证据 → 结构化计划 → 逐字定位与转述证据审查 → 版本校验写入 → 保存修订与 Markdown。单轮最多 3 个操作、1 篇新文章；空操作合法。自动维护保留旧事实和引用，不自行删除、重命名或合并知识。

问答路径：优先检索有效 Wiki → 收集有效来源与原文片段 → 受限上下文生成 → 引用定位校验；必要时使用文档检索补充。文档检索采用 SQLite FTS5 与词法回退，Wiki 采用关键词评分。无模型配置时返回证据，不能将其称为生成答案。

## 来源一致性

`update-source` 保持文档 ID，从收件箱保存新版归档，并在 SQLite 事务内再次验证旧哈希，保存旧元数据和逐页/块快照、替换索引、重置编译状态并标记关联文章。新旧资料同名不会自动建立关系；若已有另一有效来源，使用显式替代关系。

撤回与替代保留当前正文；逻辑删除先保存历史，再清理当前页和 FTS5，保留文档墓碑。三者都使受影响文章进入审查、撤销旧执行权，阻止失效引用进入默认问答。重复输入若属于失效来源或历史版本，则保留并要求审查，不静默重新引入。删除原文件、全部历史及备份属于尚未实现的物理擦除。

## 调度与模型预算

持久化任务保存指纹、执行令牌、状态、下次时间、稳定次数和失败次数。任务领取时锁定数据库并校验指纹。稳定内容指数冷却，减少模型调用而不删除正文；新文章版本重建任务。失败有限重试，审查不能由 `force` 绕过。实际周期由宿主触发，当前没有常驻调度服务。

卡片、选页、原文和输出都设置预算。维护来源上下文上限为 16000 字符，合并任务与文章上下文上限为 32000 字符；这些是字符上限，不能声称等于特定模型的 token 窗口。较大资料需要拆分或后续分层处理。

## 工程验证与已知限制

单元及集成测试验证引用、修订、回滚、来源更新/删除、事务失败恢复、任务所有权和文档定位。CI 覆盖 Windows/Linux、Python 3.10/3.14，另做静态检查和发布包审计。覆盖率门槛 80% 衡量代码执行范围，不是知识准确率。

合成评测分别测检索召回、答案关键词、引用定位、维护与证据判断。公开演示采用脚本计划，不能当作真实小模型自主维护成功。模型语义判断可能误判；生成答案的引用定位有效，也不能证明所有说法得到证据支持。

当前边界：无向量检索与 reranking、无 OCR/多模态摄取、无多用户鉴权或跨设备同步；数据库和文件系统无法保证断电时跨资源原子；模型生成期间的来源变化不具备贯穿整个调用的快照隔离。下一步应优先测真实检索缺口，再评估向量与重排，不根据功能名堆叠系统。
